# Проверка S3-бэкенда на MinIO

Из каталога `Task2Advanced` при запущенном Docker Desktop в режиме Linux-контейнеров выполните одну команду. Синтаксис одинаков для PowerShell и Bash.

```sh
docker compose run --rm -T check
```

Первый запуск загружает три образа. Compose запускает MinIO и создаёт приватный бакет с версионированием. Два клиента Terraform работают в разных каталогах с разными копиями служебного каталога `.terraform`. У них общий ключ объекта в S3. Встроенный ресурс `terraform_data` позволяет проверить механизм состояния без токена и виртуальной машины.

Образы MinIO и клиента `mc` загружаются из публичного зеркала GHCR по фиксированным SHA-256. [Происхождение образов](https://github.com/Salk-Harnessing-Plants-Initiative/bloom/issues/828)

1. Первый клиент начинает `apply` и удерживает блокировку. Второй получает ожидаемую ошибку `Error acquiring the state lock`.
2. Первый завершает запись. Второй читает выходное значение, получает пустой план и проверяет отсутствие локального файла состояния ресурсов. Затем рабочая конфигурация из `terraform/` проходит `init` и `validate` с тестовым адресом S3. Через `state list` она видит тот же `terraform_data.marker`. Для этого шага потребуется доступ к зеркалу Terraform.
3. Второй клиент удаляет тестовый ресурс. Первый видит пустой список. Признак успеха — строка `PASS` и код выхода 0.

При повторении тест использует отдельный ключ в бакете. Порты MinIO доступны только внутри сети Compose. Пример использует тестовый пароль для локальной сети. Для удаления контейнеров и тома с тестовыми данными выполните из той же папки:

```sh
docker compose down -v
```

Проверку реальной ВМ и запуска в GitHub Actions описывает [README задания](README.md).
