# «Будущее 2.0» — проектная работа, спринт 11

Медицинская компания приобрела банк и готовит подключение фармкомпаний и производителя медицинского оборудования. Сейчас отчёты, интеграции и часть операционных правил зависят от SQL Server 2008, PowerBuilder и шины Apache Camel. Проект описывает переход к самостоятельным доменам и порталу, где сотрудники строят отчёты в пределах своих прав. Медицинские карты, истории болезни и результаты исследований остаются в клиническом контуре.

## Как проверить локально

Для первых двух заданий нужны Docker с Linux-контейнерами, Compose v2 и доступ к реестрам образов и зеркалу провайдера. Запускайте команды из корня репозитория. На Windows их можно вставлять в PowerShell по одной.

```sh
docker compose -f Task1Advanced/compose.yaml run --rm -T check
docker compose -f Task2Advanced/compose.yaml run --rm -T check
docker compose -f Task2Advanced/compose.yaml down -v
```

1. В Task1 Terraform проверяет конфигурацию и выполняет по два теста с подменой ответов провайдера для каждого окружения. Ожидаемый итог — три сообщения `2 passed, 0 failed`.
2. В Task2 первый клиент записывает состояние в приватный тестовый бакет, второй проверяет блокировку и читает результат. Рабочая конфигурация из CI подключается к тому же бакету. Успех обозначен строкой `PASS`. Последняя команда удаляет только локальный стенд и его тестовый том.
3. Для Task3–Task5 откройте README задания. Диаграммы SVG и текстовые материалы доступны на GitHub, формулы TCO — в книге Excel.

## Ручная проверка Yandex Cloud

После локального ревью начните с [инструкции для dev в Task1](Task1Advanced/README.md). Подготовьте CLI, публичный SSH-ключ и параметры существующей подсети, изучите план, создайте ВМ, сверьте диски и вывод Terraform. Завершите проверку удалением ресурсов **до перехода к Task2**, чтобы освободить квоты учебного облака.

Затем пройдите [ручной сценарий Task2 до слияния](Task2Advanced/README.md#ручная-проверка-в-yandex-cloud-до-слияния) с приватным бакетом. Проверяются сохранение состояния между запусками, повторный план и удаление через тот же бэкенд. Условия запуска GitHub Actions с одобрением описаны в том же задании. Платные ресурсы создаются только при ручной облачной проверке.
