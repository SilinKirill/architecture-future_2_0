# Каталог доменных событий

Каждое событие сообщает о подтверждённом факте. Издательский сервис берёт его из outbox владельца. Имена и границы согласованы с [картой контекстов](bounded-contexts.svg) и [Event Storming](event-storming.svg). Правила транзакций приведены в [каталоге агрегатов](aggregates.md).

## Общий контракт

- `event_type` — имя факта из каталога, `schema_version` — версия контракта сообщения. Совместимость проверяется в Schema Registry. При несовместимом изменении владелец согласует новую версию и период параллельной поддержки с подписчиками.
- `event_id` — уникальный идентификатор факта, неизменный при повторной публикации. `producer` — контекст-владелец, `region` — регион операции, `occurred_at` — время подтверждённого бизнес-факта в UTC. Бизнес-день для банковских движений задаёт дата проводки, для остальных фактов — согласованный календарь региона.
- `aggregate_type`, `aggregate_id`, `aggregate_version` определяют сущность и зафиксированную версию. Ключ партиции составляют `producer`, `region`, `aggregate_type` и `aggregate_id`. Версия увеличивается при транзакциях агрегата. Разрыв между версиями в одном контракте допустим, если промежуточное изменение не породило опубликованного события. Публикатор сохраняет порядок фактов одного агрегата в его потоке. Между разными ключами и потоками используется корреляция по идентификаторам, поскольку общего порядка доставки нет.
- Там, где время в конверте полностью передаёт момент операции, payload его не дублирует. Поля `amount_minor` и `currency` рассматриваются как одна величина. Проводка расчётов по счёту имеет `posting_id`, используемый при сверке и повторном чтении.

## Источник, смысл и подписчики

`Продукт` в таблице означает сервисный обработчик домена с доступом к утверждённой схеме. Интерактивный доступ сотрудников проходит через опубликованные витрины и правила SQL-шлюза [архитектуры Task3](../Task3Advanced/architecture.md). Ключ корня уже находится в конверте. В последней колонке перечислены дополнительные поля payload.

| Событие | Владелец и ключ агрегата | Смысл | Разрешённые подписчики | Минимальный payload |
|---|---|---|---|---|
| `VisitRegistered` | CLINIC · `visit_id` | Регистратура подтвердила визит. | EHR · закрытый клинический поток. | `clinic_code`, `registration_ref` для чтения разрешённых данных регистрации в CLINIC. |
| `ClinicalStudyRequested` | EHR · `study_id` | Врач подтвердил назначение исследования для обработки ИИ. | AI · закрытый клинический поток. | `study_type_code`, `request_ref` для получения входных данных из EHR после проверки доступа. |
| `AIStudyCompleted` | AI · `job_id` | AI сохранил успешный результат обработки. | EHR · закрытый клинический поток. | `study_id`, `result_ref` для чтения результата из клинического хранилища через авторизованный сервис. |
| `AIUsageRecorded` | AI · `usage_window_id` | AI опубликовал разрешённый итог использования за период. | Продукт «Использование ИИ». | `window_date`, `service_code`, `completed_count`, `failed_count`. Версия в конверте относится ко всему окну. |
| `InvoiceIssued` | BILL · `invoice_id` | Клиника выставила счёт на утверждённую сумму. | PAY · интеграция расчётов. Продукт «Оплаты счетов» · срез выставленных счетов. | `billing_ref`, `legal_entity_code`, `amount_minor`, `currency`. |
| `PaymentPosted` | PAY · `payment_id` | Банк провёл оплату по счёту. | BILL · локальная проекция оплат. Продукт «Оплаты счетов» · проведённые поступления. | `billing_ref`, `posting_id`, `posting_date`, `amount_minor`, `currency`. |
| `RefundPosted` | PAY · `payment_id` | Банк провёл возврат по исходному платежу. | BILL · пересчёт остатка. Продукт «Оплаты счетов» · вычет возвратов. | `billing_ref`, `refund_id`, `posting_id`, `original_posting_id`, `posting_date`, `amount_minor`, `currency`. |
| `InvoiceSettled` | BILL · `invoice_id` | Подтверждённая чистая оплата впервые достигла суммы счёта в текущем цикле. | Продукт «Оплаты счетов» · ход исполнения счёта. | `billing_ref`, `settlement_cycle`. |
| `LoanAgreementSigned` | LOAN · `agreement_id` | Банк зафиксировал подписанный кредитный договор. | PAY · закрытый банковский поток для подготовки выдачи. | `funding_ref` для обращения к разрешённой банковской инструкции. |
| `BatchDelivered` | PHARMA · `delivery_id` | Площадка подтвердила приёмку количества по партии. | Продукт «Поставки по партиям». | `batch_code`, `product_code`, `site_code`, `quantity`, `unit_code`. |
| `DeviceStatusChanged` | DEVICE · `device_id` | Зарегистрирован переход устройства в новый статус. | Продукт «Состояние оборудования». | `site_code`, `device_type_code`, `status`. |
| `KpiDefinitionPublished` | KPI · `kpi_id` | Утверждена версия определения показателя. | BI · каталог определений и выбор версии для отчёта. | `definition_version`, `effective_from`, `definition_ref` на опубликованное определение и версии его входных продуктов. |

## Границы данных и пересчёт

Клинические потоки `VisitRegistered`, `ClinicalStudyRequested` и `AIStudyCompleted` читают только указанные операционные сервисы по региональным ACL. `LoanAgreementSigned` доступен только участникам банковских расчётов. Ссылки из этих событий требуют отдельной авторизации при чтении. Для аналитики владельцы выпускают отдельные продукты по согласованной схеме, например число визитов и число выдач по дню и региону. DataHub описывает происхождение и доступный уровень детализации каждого продукта.

AI строит `AIUsageRecorded` из своих подтверждённых исходов обработки. Для успеха `source_event_id` равен `event_id` из `AIStudyCompleted`. После исчерпания попыток используется ID записи внутреннего outbox о завершении с ошибкой. Журнал дедупликации с `source_event_id` остаётся у AI. Продукт получает только итог окна по разрешённым измерениям. Порог публикации малых групп и допустимые срезы утверждает владелец медицинских данных. При обновлении окна продукт заменяет его значения по ключу и более высокой версии.

Потребитель обрабатывает `event_id` один раз и атомарно записывает проекцию и отметку о применении. Для денежных фактов он дополнительно хранит уникальный `posting_id`. Подписчик PAY использует `billing_ref` для регистрации реквизитов счёта, а BILL сопоставляет оплаты и возвраты со своим счётом по той же ссылке. Возврат и исходный платёж находятся в одном потоке PAY с ключом `payment_id`. При загрузке истории или неизвестной ссылке потребитель фиксирует ожидающую корреляцию, восстанавливает запись у владельца и повторяет обработку. Несовместимый контракт уходит в закрытую очередь диагностики с `event_id` и кодом ошибки.

Повторное чтение с контрольной позиции применяет те же правила. Денежная проекция сохраняет каждую уникальную проводку, даже если та поступила после закрытия бизнес-дня. Она суммирует `PaymentPosted` и вычитает `RefundPosted` по `posting_date`, организации счёта, региону и валюте. Поздняя проводка пересчитывает свой день. Дата выставления и циклы закрытия — отдельные признаки счёта. Для текущего статуса проекция использует чистую оплату и выставленную сумму, поэтому возврат после `InvoiceSettled` снова открывает остаток при необходимости. Выполненная дважды обработка той же истории должна давать одинаковые суммы и количество уникальных проводок. Результат сверяют с банковским регистром.
