# Целевая архитектура «Будущего 2.0»

## Исходная точка и граница изменения

Сегодня оператор клиники работает через PowerBuilder. В SQL Server 2008 одновременно живут истории болезни, расчёты, кадровые данные и правила нескольких бизнесов. Кастомный Power BI и интеграции через Apache Camel зависят от этой структуры. При сотнях терабайт добавление очередного отчёта конкурирует за вычисления с существующими трансформациями. За изменением правила приходится идти в центральную команду.

Через три года клиники, банк и ИИ-подразделение ведут операционные записи в своих системах. Домен отвечает за правила изменения записи, контракт публикации, качество и поддержку своего продукта данных. Головной офис владеет определениями общих показателей и сверкой. Платформенная команда предоставляет общие средства доставки, вычисления, поиска, доступа и наблюдения. Каждый домен получает отдельные облачные учётные записи сервисов, сетевую границу и хранилище или префикс с явным владельцем.

## Как сотрудник получает отчёт

1. Клиника выставляет счёт. Расчётный сервис записывает счёт и запись outbox в одной транзакции. Банк проводит платёж и независимо публикует собственный факт расчёта. У события есть ID, версия схемы, источник, время бизнес-операции, регион и ключ агрегата. Между бизнесами передаётся согласованная непрозрачная ссылка на счёт.
2. Публикатор доставляет событие в региональный Kafka. Права записи выдаются владельцу топика, чтения — конкретным подписчикам. Schema Registry проверяет совместимость формата. В аналитические топики допускаются только утверждённые схемы и поля. Исходные документы, тексты, ссылки на снимки и результаты исследований ИИ остаются в клиническом контуре. События лечения, нужные врачам и ИИ, маршрутизируются по отдельным закрытым каналам.
3. Доменный потоковый обработчик проверяет контракт, отсекает повторы и рассчитывает витрину. Контрольная точка и версия записи позволяют повторить обработку после сбоя. При несовместимом сообщении обработчик сохраняет в ограниченной очереди диагностики идентификатор и код ошибки. Исходное сообщение разбирает владелец в разрешённом контуре. Поправка к проведённому платежу приходит отдельным фактом.
4. Продукт «Оплаты счетов» публикует в Iceberg итог по дню, региону, организации и валюте. Владелец указывает гранулярность, правила учёта возвратов, свежесть, версию, происхождение и контакт в DataHub. Для примера KPI «Чистая сумма оплат» складывает проведённые платежи за вычетом возвратов в одной валюте. Дата выставления счёта и дата проводки — разные измерения. Обработчик отсеивает повторные доставки по `event_id` и учитывает каждую проводку один раз по `posting_id`. Так два частичных возврата по одному платежу сохраняются в отчёте как отдельные проводки. Сверка с регистром банка выявляет пропуски.
5. Сотрудник входит в портал через корпоративный IdP, находит продукт по бизнес-термину, выбирает меру и срезы, сохраняет свой отчёт. Каталог показывает, кто подтверждает доступ. SQL-шлюз применяет права домена, региона, строк и колонок к проверенной личности пользователя, в том числе при выгрузке. Интерактивный пользователь не получает ключей S3. Головной офис получает согласованные региональные агрегаты. В аудит попадают пользователь, продукт, версия политики и факт чтения.

**Критерии приёмки для пилота** предложены для обсуждения с владельцами. При двойной доставке сумма отчёта совпадает с результатом однократной обработки. После закрытия операционного дня расхождение с банковским регистром по числу и сумме проведённых платежей и возвратов объяснено до последней записи. Целевой p95 свежести потоковой витрины — 5 минут от времени события; p95 открытия типового отчёта — 10 секунд на согласованной выборке запросов и нагрузке. Просроченная витрина показывает время последнего подтверждённого обновления. Отказ в доступе сохраняется при прямом SQL-запросе и экспорте отчёта.

## Где хранятся данные

- **Медицинский контур.** Карты, истории болезни, снимки и результаты исследований доступны лечащим специалистам и медицинскому ИИ по отдельному клиническому маршруту. Полная выгрузка DWH в аналитический бакет создала бы обход этой границы. Для миграции аналитики извлекаются только разрешённые поля из явно перечисленных источников. В общую аналитику ИИ поступают согласованные операционные показатели использования сервиса без результата исследования и идентификатора пациента.
- **Банковский контур.** Банк владеет счетами, договорами и проводками. Междоменным потребителям выдаются минимальные контракты расчётов и агрегированные показатели. Кредитное досье остаётся у банка. Ограничения на размещение, сроки хранения, круг получателей и межрегиональную передачу для каждого набора согласуют владельцы и специалисты по защите данных перед публикацией.
- **Аналитическая платформа.** Kafka хранит разрешённые события на ограниченный срок для повторного чтения. Flink поддерживает доменные проекции. S3 и Iceberg хранят версии аналитических таблиц. Технический каталог Nessie указывает читателю на согласованную версию таблицы. DataHub описывает набор для человека, Trino выполняет запрос, BI-портал строит отчёт. Контракт и политика доступа версионируются вместе с продуктом.
- **География.** Первичный приём, обработка событий, ключи шифрования и копии данных размещаются в разрешённом регионе. Для выхода ещё в два-три региона тиражируется конфигурация регионального сегмента. Межрегиональная публикация разрешается по перечню агрегатов и получателей. Согласование состава данных и размещения предшествует подключению первого источника.

## Как подключить ещё один бизнес

Например, производитель оборудования передаёт изменения состояния отдельных устройств. Домен эксплуатации через адаптер принимает данные поставщика и публикует событие `DeviceStatusChanged`. По последнему состоянию каждого устройства витрина рассчитывает количество исправных устройств по типу и площадке. Платформенная команда выдаёт пространство имён, права, шаблон потока и наблюдение. Владелец домена регистрирует продукт, публикует пробный набор, проверяет полноту и заключает соглашение о свежести с клиниками. После сверки портал открывает витрину эксплуатации. Аналогично фармкомпания публикует сведения о поставках по партии. Новый домен меняет собственные обработчики и контракты; существующие потребители продолжают читать поддерживаемую версию.

## Переход и вывод легаси

**Судьба действующих систем.** Банковские сервисы на Go и Java сохраняют проводки и кредитные договоры, получают outbox и переносятся в отдельное окружение банка. Сервисам ИИ на Python выделяются закрытое вычислительное окружение и самостоятельный цикл выпуска моделей. Бизнес-правила из DWH по одному переходят в сервисы доменов. Операторам клиник вводят новый интерфейс по мере покрытия сценариев PowerBuilder. Для каждого востребованного отчёта Power BI владелец подтверждает формулу, права и сверку с новым отчётом перед выводом старого. Это позволяет направить переработку на зависимости, которые сегодня замедляют изменение показателей.

| Срок от начала | Действие | Условие переключения |
|---|---|---|
| До 2 месяцев | Утвердить архитектуру, владельцев, границы медицинских и банковских данных. Снять исходные замеры отчётов, согласовать пилоты, источники и приоритеты. | У каждого пилотного показателя согласованы формула, поставщик, потребитель и способ сверки. |
| 0–6 месяцев | Пилот расчётов по счетам. Адаптер читает разрешённую выборку из SQL Server и преобразует формат Camel. Создать версионируемые события, DLQ и первые витрины. | Теневой расчёт на тех же операциях, контроль повторов и восстановления после остановки. Пилотный отчёт принят владельцем. |
| 6–12 месяцев | Подключить операционные показатели клиник, банка и ИИ. Ввести портал, каталог, конструктор отчётов и матрицу доступа. | К концу 12-го месяца сотрудники действующих доменов сами находят набор, строят отчёт и повторно открывают его; тесты междоменных запретов пройдены. |
| 12–18 месяцев | Перенести критичные правила из процедур DWH в сервисы владельцев, добавить потоковые витрины, заменить прямых потребителей Camel адаптерами. | Для каждого перевода зафиксированы контрольная позиция, единственный писатель, сверка и точка возврата. |
| 18–36 месяцев | Подключать фарму, оборудование и регионы через доменные контракты. Вывести точечные синхронные вызовы из критического пути. Перевести оставшихся потребителей PowerBuilder и Power BI. | Критические операции выполняются при выключенных мостах. Карта зависимостей, аудит чтений и репетиция восстановления подтверждают возможность остановки Camel и старого DWH. Архив хранится по согласованным срокам. |

**Возврат при сбое.** До передачи прав записи домену прежняя система остаётся владельцем операции. После переключения допустим возврат чтения на сверенную витрину с пометкой времени среза. Для возврата записи команда останавливает приём, переносит подтверждённые за интервал операции из журнала, сверяет остатки и возобновляет работу с одним владельцем. Решение принимает владелец процесса совместно с дежурным инженером.

**Надёжность.** Отказ аналитики задерживает отчёты; клиника продолжает приём, банк — проведение операций. Реплики брокера и хранилищ распределяются по зонам, очереди измеряются по отставанию и возрасту старейшего события. Для пилота предложены RPO 15 минут и RTO 4 часа для аналитической витрины; восстановление проверяется replay из подтверждённой контрольной позиции и сверкой с операционным источником. Целевые RPO/RTO клинической и банковской транзакционных систем согласовываются отдельно. Условия реакции и владельцы описаны в [плане управления рисками](risk-management.md).
